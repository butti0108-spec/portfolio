## 1. 役割

| 誰 | 役割 |
|----|------|
| **敦さん** | 方針・本番公開・迷う判断・承認。実装の**でき具合の確認**と、OK後の commit／push 合図 |

## 2. フェーズ完走（最重要・2026-09-21）

スレッドで「いま熱い話」が上がっても、**進行中の実装フェーズを途中で切り替えない。**

AIは今の会話を最優先にしたくなるが、敦さんとクルの話は、ソル実装の **1〜2個先（または直後）の想定・修正案** であることが多い。熱さでフェーズを飛ばすと分散し、どこまでやったか分からなくなる。

### やり方

1. **いまのフェーズを最後まで完走する**  
   実装 → 自己通し（ブラウザ）→ 敦さん確認 → その場修正（あれば）→ **敦さんOK** → まとめて commit/push → クル確認（コード＋通し）→ 区切りOK
2. 先の話・気になる修正は **メモに溜めるだけ**（その場でソルの作業を切り替えない）
3. フェーズが終わってから、溜めた話を材料に **次のフェーズを1本だけ** 作る

### 禁止

- 「今しゃべってるから」で別機能へジャンプ
- フェーズ途中で寿司レイアウトと保存フォルダを混ぜる、など横断盛り
- 完了していないのに次フェーズ指示を出す

### 例（保存まわり）

区切り1（保存ゲート）→ 2（ZIP再開）→ 3（フォルダ）が本線なら、途中で寿司見た目の話が出ても **3が終わるまで寿司は次フェーズ待ち**。

## 4. Git と確認（2026-09-29 差し替え）

正本: [実装は敦さんOK後にまとめてpush](./2026-09-29-実装は敦さんOK後にまとめてpush.md)

### 意図

- 細かい修正ごとの push は時間がかかる
- 戻し・直しを都度 push すると、**どの push が正しいのか分からなくなる**

### ソル（毎回）

1. 行動前に対象リポ＋連絡リポを `git pull`
2. 指示範囲だけ実装
3. **ブラウザ通し**（普通の道＋ありえない操作・戻り・連打・変な順・更新など）
4. 表示・動きに問題がないことを確認し、**敦さんの確認待ちで止める**（この時点では commit／push しない）
5. 敦さんから修正があればその場で直す → また通し → また確認待ち
6. **敦さんが OK と言ったあと**、同じ区切りでまとめて commit → `push origin main`
7. 必要なら `kurusorumessage` の `pending` に報告（hash・**通しでやったこと**・次は指示待ち）

敦さんOK前の変更は、ローカルに残してよい。細かい直しごとに push しない。

### 敦さん（毎回）

1. 実装の画面を見て、できているか確認する
2. 修正があればその場で出す
3. OK なら commit／push の合図を出す

### クル（毎回）

1. 指示を切る（ここは変わらない）
2. **敦さんOK・push のあと** pending と GitHub 差分を見る
3. **可能なら自分でも同等の通し**（Askなら読み確認＋敦さん／Agentで通し、と明示）
4. OKなら次フェーズ。NGなら直し指示（フェーズは切り替えない）

コードだけ見て「完了」は禁止（2026-09-21・敦さん指摘）。甘い完了は差し戻す。

### 禁止（共通）

- Pages 入口削除（`index.html` 等を消したまま push）
- 秘密・巨大 zip を追跡に入れる
- `docs/確定/` の独断改変（案は進行中）
- force push／git identity の無断変更
- 同時に同じファイルを奪い合う（被りそうなら一回止めて pending に「待ち」）
- **敦さんOK前の自動 commit／push**（細かい直しの都度 push も含む）

## 5. 指示書（クル→ソル）に必ず入れるもの

1. 目的（1行）
2. フェーズ名／区切り番号
3. やってよい範囲・触るパス
4. **禁止**（help・確定・Pages・次フェーズなど）
5. 文言（仮なら「仮」と明記）
6. 参照（どの正本・どの既存画面）
7. **完了＝ブラウザ通し必須**（**今回変えた道だけ**を列挙。型の毎回説明はしない）
8. **敦さんOK後**にまとめて commit/push（OK前は push しない）＋ pending 報告フォーマット
9. 「次は指示待ち。勝手に次フェーズへ行くな」
10. **末尾固定**: `docs/確定/2026-09-29-指示は短く-確認は8765だけ.md` の確認4点（8765一度だけ／ダメなら一行で止める）

慣れた相手への指示本文は、**型の名前＋今回だけ違うところ**で足りる。

## 6. 完了の定義

```text
自己完了（敦さん確認前）＝ コードを書いた ＋ 自分でブラウザを触った ＋ 変な操作でも破綻しない
                              ＋ 「安心して終われる／引き継げる」と取れた

区切り完了（Gitに載せる）＝ 上記 ＋ 敦さんOK ＋ まとめて commit/push
                              ＋（必要なら）pending に通し内容
                              ＋ クル確認
```

「動くはず」だけでは完了ではない。**OK前に push しただけ**も区切り完了ではない。

**判断の一句（2026-09-29・敦さん）**：自分が「これで完了」と言って、**安心して終われるか／次に引き継げるか**。人間の「気持ちいい／スッキリ」は安心・ほっとする・納得の言い回し。実装側ではその理解でよい。チェックを埋めただけでは足りない。見た結果で次に渡してよい、と自分で取れたときだけ自己完了と言う。

通しの開き方・ループ禁止: [2026-09-29-指示は短く-確認は8765だけ](./2026-09-29-指示は短く-確認は8765だけ.md)

## 8. 一言まとめ

- **フェーズは完走。熱い話はメモ。次フェーズは終わってから。**
- **ソルは書いて通し、敦さんOK後にまとめて push。クルは指示を切り、push後に確認する。**
- **細かい直しごとの push はしない（どれが正か分からなくなるのを防ぐ）。**
